# Architecture

`hermes-auto` owns the queue, runtime bridge, execution policy, status and scheduling. It imports no adapter modules and has no mailbox credentials or provider dependency. Python entry points discover only installed adapters.

```text
hermes-auto-todoist ──┐
hermes-auto-gmail ────┼── durable event queue ── reserved session ID ── Hermes session API
hermes-auto-proton ───┘                                  │
                                              full-agent or restricted worker
```

Adapter API: export a `Source` class with `defaults() -> dict`, `poll(config, store)` and `setup(config)`. Optionally `finish(config, job) -> str`: called once when the user archives the job's session after it was seen open (`ready`/`needs_attention` -> `done`); it closes the source item (Todoist completes the task) and must be idempotent against items already closed at the source. `poll` stays read-only. Register it under `[project.entry-points."hermes_auto.sources"]`. `poll` may read its provider and enqueue immutable source events. `setup` is an explicit user command for reversible opt-in label creation, never called by the scheduler. Source failures block that source's pending jobs without disabling unrelated sources.

Events use unique `(event_key, generation)` records. Normal polling uses generation zero. Only `new-session` allocates another generation and a new session ID. The title is presentation only. A user may rename or delete a Hermes conversation without changing event identity.

Lifecycle: `pending -> creating -> created -> running -> ready`. Open-only jobs go `created -> ready`. Errors become `needs_attention`; recovery converts abandoned `creating` and `running` states to the same status. Explicit retry uses `retry_pending` and the existing ID. A missing session becomes `deleted`; mail opt-out cancels pending work. A not-yet-created Todoist job can be `deferred` until its task qualifies again, preserving its reserved ID. No automatic model retry follows ambiguous completion.

The bridge runs in a child process with Hermes' dependencies. Runtime home (dependency activation) and session home (database/config) are separate, to support profile isolation. Since Hermes v0.22.5 every turn runs in the gateway that owns the Hermes home (the only writer of its sessions), so the bridge is a gateway client: `session.create` (source `gui`, so the Desktop platform prompt) with a frozen launch policy per job (`bridge.launch_plan`: toolsets, `max_turns`, `run_budget`, `ignore_rules` for bounded preparation, and the `routes` provider/model), then one finite `prompt.submit` (`text` = the card the transcript shows, `api_text` = the full prompt) without `unattended`, so approvals resolve to deny and clarify gets no answer. The reserved session id is the creation key (`request_id`); the gateway names the session and `Store.rebind_session` moves the job, followups and `thread_session:*` to it. `open` jobs (brief, plan, proposals) are imported through `session.mutate import` under the reserved id. The bridge reads state.db only read-only (`SessionDB(read_only=True)`, SQLite `mode=ro`) and patches nothing in Hermes.

Bots: each job's session lives in one Hermes profile of the same multiplexed gateway (`bots.py`, config `bots`). The bridge request carries the profile's home as `hermes_home`, so `connect_gateway` gets a ticket for that profile exactly like `hermes -p <bot>`, and state.db reads (inspect, archive states, excerpts) open that profile's database. `bots.choose` picks the profile once, before the session exists, and `jobs.profile` keeps it (`''` = a job from before bots: the default profile): internal sources (brief, plans, proposals) go to `bots.default`; third-party content goes to a read-only bot (`bots.read_only`) named by the first matching rule, else `bots.inbox` (a rule naming a working bot is ignored for it); full-tools jobs go to the first matching rule naming a working bot, else `bots.default`. A `↩` reply carries the bot of the conversation it answers (`payload.bot`, from `Store.session_profile`) and stays there when that bot is read-only.

The tool boundary is the read-only bot's own profile configuration: `platform_toolsets.cli` names only the `hermes-auto` toolset and `session_search`, `agent.disabled_toolsets` removes terminal, files, browser, web, code execution, delegation, memory, skills and the rest, and the gateway refuses a `session.create` asking for more. Hermes Auto also freezes `[hermes-auto, session_search]` (private channels: no tools) per session, plus the `routes` account (one inbox bot serves private matters and TapIn work; the work account comes from the route, Slack DMs stay on the private one). The bot profile writes no memory (`memory.memory_enabled`/`user_profile_enabled` false) and runs no background review (`auxiliary.background_review.enabled` false), so third-party text never persists; `profile_problems` checks these too. The `hermes-auto-guard` plugin (`guard_plugin/`, installed into `<profile home>/plugins/hermes-auto-guard` with `scope.json` by `hermes-auto install-guard`) is enabled only in those profiles and applies to every session there (no per-session registry): the read tool `hermes_auto_read` runs one grammar-checked read command without a shell, limited to the bot's read families (`google`, `todoist`, `github`, `linear`, `slack`), and the `pre_tool_call` hook refuses any other tool and a cross-profile `session_search`. Refused calls get a neutral `{"skipped": true, "note": ...}` result. Skills are read as raw text. Before creating or running a session the bridge checks the target (`bridge.require_bot`): third-party content only in a read-only bot whose config passes `profile_problems` and whose plugin the running gateway reports loaded in the expected version (`plugins.list` on that profile's connection); a full-tools run only in a working bot whose approvals are not `off` (the turn is finite, so Hermes resolves approval-gated actions from `approvals.single_query_mode: deny`). Otherwise the job is refused before anything is sent (`last-error.json`, `needs_attention`, fix and `new-session`). Sessions created without a matching `launch_request` are refused with a `hermes-auto new-session` hint.

The package has no exactly-once side-effect guarantee across an LLM and external systems. It avoids those effects during unattended preparation and stops on ambiguous outcomes. Recovery, deletion and deliberate regeneration are distinct actions.

Provider details stay in adapters. The core's `observe_stream` is provider-neutral: mark first observations as a baseline; persist seen item IDs and eligible events atomically. Gmail uses provider thread/message IDs. Proton maps RFC reply chains into stream/message IDs. Todoist uses task IDs plus the latest available completion timestamp for recurring occurrences.

Push acknowledgements follow durable delivery. Ticks acknowledge successful source reads at their start timestamp, never at completion; failed sources retain their trigger and persist retry backoff. `source_backlog:<name>` schedules the next batch. The relay exposes an epoch, retained range and per-source health; the client catches up on resets/gaps and rate-limits fallback for stale listeners. Mark adapters return per-item `done`/`unsupported`/retry outcomes; cumulative Slack markers cannot overtake undelivered earlier items. GitHub marks the thread only when it has no update newer than the shown one. Linear marks single notifications. Linear is polled (`poll_seconds`), not relayed: a member's inbox has no push. Proton marks scoped IMAP UIDs rather than searching sender-controlled Message-IDs.

Push listeners (`hermes_auto.listening`, opt-in services per adapter: Slack Socket Mode, Proton IMAP IDLE) never touch the database; they write `<name>-listener.json` (times and ids, no text) and run `tick`; an adapter's optional `due(settings, store, last_poll, now)` turns that tick into a check of that source only (`fast_sources`).

Limits in 0.1: no attachment extraction; no cross-mail-provider deduplication. Adapter polling is intentionally opt-in. Agent runs start in the background (`Hermes.start`/`collect`), so a tick does not wait for them. Inbound webhooks (Todoist, Gmail Pub/Sub) go to the Cloudflare Worker in `gateway/`, which forwards ids only through the relay queue; the Mac never opens an inbound port. Versions are aligned for this first release, but distributions and dependencies are separate.

## Sorter (`triage`, opt-in)

`hermes_auto.triage` runs after the adapters' `poll` when `config.triage.enabled` is true. Adapters that implement it supply candidates; the core owns decisions, state and prompts.

- Mail adapters: `inbox(config, store, limit, since_ms=None) -> (candidates, cursor_key, cursor)`. A candidate carries headers, a text excerpt, `thread_id` and `sent` (the user's earlier sent messages in that thread: time and recipients). The first call only returns a baseline cursor. The cursor is committed together with the decisions; a read or a step that fails before that commit re-reads the same mail.
- A candidate in a thread the user wrote is routed to the Hermes session that sent it: the bridge's read-only `find_session` requires a correlated successful send receipt from a recognized `google_api.py gmail send/reply` tool invocation within a bounded window around each send time and resolves compression continuations. Unrecognized send mechanisms (including Proton sends) fall back to normal classification rather than guessing. Mere mentions of a subject or recipient and ambiguous matches do not route replies. The thread then stays mapped to that session (`meta thread_session:*`). Other candidates get one batched model call (`classify`, Hermes `call_llm`, provider/model from `triage.provider`/`triage.model`, overridden per item by the first matching `routes` rule; a batch mixing routes is split into one call per route): `session` (enqueued job that posts a short notice), `brief` (collected) or `skip`.
- Each route's call stands alone (`classify_routes`). When one fails (e.g. the default account rate limited), the other routes' items are decided, get their sessions and the cursor moves in the same commit; the failed items go to `meta triage_pending:<source>:<account>` (not recorded in `triage_items`, not marked read) and the check reports `sorter <source>: ...`. That line is not a source read failure, so the source gets no `source_retry` backoff and keeps being read at its nudges. Waiting items retry with their own delay (60 s doubling to 30 min; `fast_sources` makes the source due then, even with nothing new) or earlier together with a new item on the same route. `status.triage_pending` lists them with the last error.
- `routes` (`config.model_route`): `{"match": {...}, "provider", "model"}` rules matched against the job source (or item kind) and payload. `Hermes.start`/`run` put the job's route into the bridge request and the bridge passes it to the gateway's `session.create(provider=, model=)` (and to `model`/`model_config` of an imported `open` session); an empty route keeps Hermes' configured model. Thread replies are enqueued with the item payload, so they inherit the route.
- Third-party mail never runs with tools beyond reads. A mail or Slack/GitHub session is created in a read-only bot with the guard's read toolset only (see above); the card is the visible first message and the full prompt its `api_content`. A reply in a thread always opens a new `↩` session; the old one is never written to.
- Todoist: `inbox_tasks(settings)`, `outline(settings, store, hours)` (lists, sections, sample titles; cached) and `apply(settings, task, decision, label)`. A task is classified after it has sat in the Inbox for `settle_minutes`. With `triage.todoist.apply` the adapter moves it, sets an evident priority, adds the agent label and reads it back; a labelled task is only started when `auto_start` is on (then `triage_run`, which the due-date poller leaves alone); otherwise the questions session asks whether to start it. Open questions go into one `questions` session. This is the only scheduled source write besides `finish`.
- Decisions are persisted before Todoist writes. Failed applications retry their saved decision using a fresh full task read, including tasks already moved to the decided destination. A move by the user to a different project stops retries. Three failed attempts become `needs_attention`, visible alongside `user_changed` in `status.triage_issues`. Successful plans are durably queued with unique batch IDs. With `apply=false`, proposals are delivered in the brief without modifying tasks. Applied tasks become `planned`; rows from older versions (`moved`, `asked`, `baseline`) that sit in a review filter take one fresh decision through the same durable path. A plan that offers a start marks the task as proposed only after its apply succeeded. A reply whose session is gone or held by Desktop (`owned_by`, or `SessionBusy` during the run) opens one `↩` session per thread: the thread mapping moves to it unless it already points at a third session, and only that thread's pending replies follow.
- Interrupted replies become `needs_attention`; `status` exposes them and `retry-followup ID` checks for prior delivery before explicitly queueing a retry.
- GitHub threads (`github_quiet`): every push, edit or bot comment updates a notification thread, so a candidate in a thread that already has a session is not routed straight to a `↩` session. The adapter reports the newest comment or pull request review as `activity` (`comment:<id>`/`review:<id>`, author, bot). No activity, a bot, or the activity already recorded for the thread (the last `triage_items` row, or an earlier update in the same batch; rows without `activity` compare the shown comment text) is recorded as `skip` and marked read at once. A new comment or review from a person goes to the classifier with `followup: true`; `session` continues as a `↩` session, `brief` and `skip` open nothing. A `↩` title keeps a single arrow.
- Slack (`hermes-auto-slack`) implements the mail adapters' `inbox` contract. Candidates carry `kind: "slack"`, one per conversation burst (`<channel>:<thread_ts>@<last ts>`), `thread_id` = the DM channel or `channel:thread_ts`. Discovery: Slack MCP search (DMs, mentions, the user's own recent channels) and `conversations.history` of `watch_channels` (each top-level post is its own candidate keyed `<channel>:<post ts>`, `why: channel`, read state from the channel marker), then Web API `conversations.history`/`replies`; a thread counts when its parent is `subscribed` or the user wrote in it. The cursor (`since`, baseline `start`, per-conversation hand-over ts) is committed with the decisions. Slack items get their own classifier prompt (`slack_criteria`), `triage_items.kind = 'slack'`, a `## Slack` brief section and the `deny_tools: "slack"` read profile (agent budget; `bridge.slack_read_command`). Sources may set their own `poll_seconds`: `tick` then runs a partial check (`only`) for them between full checks.
- LinkedIn notifications use provider thread IDs only; names and links in the message body never join separate threads.
- Gmail drains all result pages with a timestamp/ID cursor and overlap; Proton decodes unknown charsets using a replacement-character fallback.
- At each `brief_times` slot, collected mail and unapplied task proposals become one `brief` session. `brief` and `questions` are internal sources: enabled with triage, never finished by archiving.
- Optional: `triage.hide_sessions` marks created sessions hidden; the Desktop plugin in `desktop-plugin/hermes-auto` then lists every `☀ ` session on its "Auto" page. Off by default.
- Full-agent jobs per check are capped by `max_agent_jobs_per_run` (default 1): a check holds the lock for the whole run.
